# Threat model: synthetic multi-tenant notes API

## Scope and evidence

This is a static, conditional assessment of the supplied fixture, not a claim about a running deployment. The confirmed context describes an internet-exposed multi-tenant API, trusted HTTPS termination and authentication middleware, authenticated user IDs, and confidential tenant notes ([README.md:1](README.md#L1); [previous-check-in.txt:3](previous-check-in.txt#L3)). Malicious authenticated tenants are in scope; operator host compromise and CI are excluded. Availability and abuse costs are considered conditionally because their scope was not resolved. No runtime, network, database, middleware, routing, proxy, or log-sink behavior was verified.

The prior questions are unresolved, not affirmative facts ([previous-check-in.txt:5](previous-check-in.txt#L5)). For analysis, assume a tenant must not read another tenant's notes; finer owner/member/share policy is unknown. Assume an authenticated tenant can reach each relevant handler only in the scenarios below; actual route access is unknown. Note ID entropy, lookup scoping, unauthorized response behavior, URL policy, egress, reachable services, credentials, log readership and redaction, and upstream limits remain unknown. If an independent control already enforces a condition, the associated likelihood is lower; it must be verified before treating the risk as mitigated.

Likelihood describes feasibility under each stated condition, not observed frequency. Impact describes a plausible consequence, not established damage.

## Assets and boundaries

- Confidential note content and tenant/user associations cross from the database into responses. The authenticated user and requested note ID are different trust inputs; authentication alone does not establish permission for that object.
- Authorization headers, potentially bearer credentials, and error details cross into the logging system; log readers and retention form another boundary.
- User-supplied preview URLs cross from an authenticated client into the server's outbound network identity, and remote response bytes cross back through the server. Internal services, metadata credentials, network capacity and third-party services are potential assets only if reachable.
- API availability, memory, bandwidth and outbound costs are conditional assets. The trusted proxy and identity middleware are context assumptions, not independently inspected controls.

## Threats and controls

| Abuse path and evidence | Conditional likelihood / impact | Existing evidence vs recommended controls |
| --- | --- | --- |
| **Cross-tenant note read.** An authenticated tenant supplies another tenant's ID; `getNote` passes only that ID to `db.findNote` and returns its result ([server.mjs:1](server.mjs#L1)). The handler itself supplies no actor or tenant scope. Exploitation requires reaching the handler, learning or guessing an ID, and no effective authorization in routing or the database. | High likelihood if IDs are obtainable and no other object authorization exists; otherwise unknown. High impact: confidential note disclosure. Unguessable IDs reduce discovery but are not authorization. | Trusted authentication is stated, but object authorization is not demonstrated. Enforce the actual owner/member/share policy with authenticated identity and tenant scope in a constrained database query or equivalent mandatory authorization layer; deny by default and make missing and unauthorized responses indistinguishable where appropriate. Test cross-tenant and same-tenant unauthorized access, including direct handler paths. |
| **Server-side request forgery and response disclosure.** A caller gives `preview` an internal or otherwise restricted URL; it fetches the supplied URL and returns response text ([server.mjs:2](server.mjs#L2)). Redirects or DNS changes can move a seemingly allowed hostname to a restricted destination. Actual fetch behavior, route access, network reachability and upstream policy are unverified. | High likelihood if unrestricted invocation and reachable sensitive destinations exist; otherwise unknown. High impact if internal data or metadata credentials are returned; potential downstream compromise depends on what is reachable. | No destination validation is visible in the handler; egress policy is unknown. Restrict preview to a business-justified allowlist of HTTPS destinations and ports; reject credentials in URLs and private, loopback, link-local and metadata addresses for IPv4 and IPv6. Resolve and enforce the destination at connection time, revalidate every redirect or disable redirects, and apply network egress restrictions as defense in depth. Test redirects, DNS rebinding and address variants against the actual stack. |
| **Credential or sensitive error exposure through logs.** On an error path, `logError` passes the authorization header and error object to the logger ([server.mjs:3](server.mjs#L3)). A log reader could obtain a reusable credential or confidential error content if those values are present and retained without effective redaction. | Medium likelihood conditional on the error path and sensitive values reaching accessible logs; unknown otherwise. High impact if a valid bearer token can be replayed, or sensitive note data is present. | The logger receives the header explicitly; downstream filtering, access and retention are unknown. Omit authorization and sanitize error fields before logging, allowlist safe structured fields, restrict log access and retention, and verify redaction at the final sink. Rotate any confirmed exposed credentials according to incident procedure. |
| **Resource exhaustion or outbound abuse.** A caller repeatedly requests slow or large preview responses; `r.text()` consumes the response as text and the handler shows no timeout or size limit ([server.mjs:2](server.mjs#L2)). It may also direct traffic at third parties, subject to actual egress and routing. | Medium likelihood if reachable and limits are absent; unknown otherwise. Medium to high impact on memory, bandwidth, availability or cost, depending on deployment limits. | No limits are visible in this function; proxy and platform controls are unknown. Apply per-tenant rate and concurrency limits, bounded connection and total timeouts, streaming byte caps and aborts, and outbound destination controls; test slow, oversized and repeated responses. |

## Priority and follow-up evidence

First verify the mandatory object-authorization path and outbound preview reachability, then remove secrets from logs and establish preview resource limits. These are recommended actions, not changes made in this assessment. Review actual route/middleware wiring, tenant mapping and database queries; inspect proxy and egress policies, DNS and redirect handling; inspect logger configuration and final sink access/redaction; and run authorized isolation, SSRF, logging and resource-limit tests in a controlled environment. Record results separately from this static model. Until then, missing controls and exploitability remain unknown.
