The main conditional risks are cross-tenant note disclosure, server-side request forgery (SSRF) through previews, and credential exposure through error logging. `server.mjs` provides direct evidence of the relevant calls, but the fixture does not establish their routing, surrounding authorization, egress restrictions, logger configuration, or runtime behavior. Priorities below are conditional risk estimates, not verified vulnerabilities.

## System model

### Primary components

`server.mjs` exports three JavaScript functions: `getNote` calls an injected database object; `preview` calls `fetch` and reads its response as text; `logError` passes an error and authorization header to an injected logger. The proxy and authentication middleware are described in `README.md`; their implementation and deployment are absent. No framework or build system is identifiable. Runtime handlers are distinct from the supplied check-in and exercise files; no CI or tests are evidenced.

### Data flows and trust boundaries

- **B1: Internet tenant → proxy → application:** requests may carry credentials, IDs and URLs over HTTPS to the trusted proxy; middleware supplies authenticated user IDs per `README.md`. Proxy-to-application transport, routing, caller authorization, validation and rate limits are unknown. The functions consume request fields (`server.mjs:1-3`). TM-001 through TM-005 address this input boundary.
- **B2: application → database interface:** `getNote` passes an ID to `db.findNote` and returns its result (`server.mjs:1`). The database protocol, tenant context, row authorization, validation and isolation are unknown; the function supplies no tenant argument. TM-001 addresses this boundary.
- **B3: application → URL destination:** `preview` passes a supplied URL to `fetch` and reads text (`server.mjs:2`). Scheme, destination, redirects, encryption, DNS handling, response limits, timeouts and egress controls are not established in this fixture. TM-002 and TM-003 address this boundary.
- **B4: application → logger and log readers:** `logError` sends the error and authorization header to `logger.error` (`server.mjs:3`). Logger transport, redaction, retention, access controls and validation are unknown. TM-004 and TM-005 address this boundary.

## Attacker model

### Capabilities

An authenticated malicious tenant is assumed able to choose IDs and URLs if the corresponding functions are exposed, and may induce errors if an accessible path permits it. An attacker may operate a URL destination and control its responses. These are conditional capabilities, not verified routes (`server.mjs:1-3`; `previous-check-in.txt`). Log access is a separate prerequisite, not assumed for every tenant.

### Non-capabilities

The model does not assume host or CI compromise, direct database or logger access, control of trusted middleware or proxy configuration, or the ability to forge another authenticated identity. It does not assume that a particular internal endpoint, metadata service, or usable token exists. Operator-controlled deployment policy and developer-controlled code are distinct from tenant-controlled request fields; their actual configuration is unknown.

## Top abuse paths

1. **TM-001 — Read another tenant's note:** choose or obtain a different tenant's ID → submit it to an exposed read handler → if no effective tenant check exists, receive confidential content.
2. **TM-002 — Read an internal response:** submit a URL pointing at a process-reachable internal resource → preview fetches it → if response text reaches the caller and egress is unrestricted, disclose internal data.
3. **TM-003 — Exhaust resources:** point preview at a slow or large response or repeat requests → fetch and text consumption occupy resources → service availability degrades if effective limits are absent.
4. **TM-004 — Steal a credential via logs:** induce an error carrying an authorization header → logger receives it → a person or principal with inappropriate log access obtains a usable credential if it is not redacted.
5. **TM-005 — Damage diagnostic integrity:** induce errors containing attacker-controlled content → logger records it → if downstream rendering or parsing fails to preserve structure, misleading records obscure incidents or consume log capacity.

## Criticality calibration

- **Critical:** likely compromise of many tenants or core service with broad impact, such as unauthenticated access to all confidential notes, or a preview path exposing a broadly privileged service credential. Neither is established here.
- **High:** plausible substantial confidentiality or integrity harm, such as cross-tenant note reads or credential theft from unredacted logs. TM-001, TM-002 and TM-004 are high only under their stated prerequisites.
- **Medium:** material but bounded disruption or exposure, such as sustained preview-driven availability loss, or disclosure of a limited internal response without privileged data. Actual controls and blast radius determine placement.
- **Low:** limited or difficult-to-exploit harm, such as a single misleading log record with intact structured handling, or a brief failed preview request contained by effective limits.
